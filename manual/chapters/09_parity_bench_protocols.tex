\section{Protocols (pinning evaluation settings)}
Protocols pin evaluation settings such as dataset splits, image dimensions, and metric keys. This keeps long-running comparisons stable.

For YOLO26 comparisons, the pinned protocol is defined as follows:
\begin{itemize}
  \item Protocol file: \path{protocols/yolo26_eval.json}
  \item Task: \texttt{detect}, Dataset: \texttt{COCO}, Split: \texttt{val2017}
  \item Image size: \texttt{640} (enforcement is the responsibility of the export pipeline)
  \item Bounding box format: \cmd{cxcywh_norm}
  \item Primary score key: \cmd{map50_95}
\end{itemize}

A key semantic rule from the protocol documentation:
\begin{itemize}
  \item "End-to-end (e2e) mAP" dictates that the evaluator scores detections exactly as provided; it explicitly does \textit{not} apply Non-Maximum Suppression (NMS).
\end{itemize}

\section{Benchmarks}
Latency and FPS benchmarks are part of the regression testing surface.

The recommended user-facing entrypoint is now \cmd{yolozu benchmark}. The
current implementation remains artifact-first and additionally wires real
backend orchestration for \cmd{torch}, \cmd{onnx}, \cmd{engine}, and
\cmd{torchscript}, plus a conditional real \cmd{openvino} lane. TorchScript uses a declared combined-output decode path
with rows \cmd{[x1,y1,x2,y2,score,class_id]}. When the real backends can execute, the command records a real
dataset-pass wall-clock measurement. When they cannot, it still records
skipped formats honestly rather than fabricating success.

A representative canonical invocation is:
\begin{lstlisting}[language=bash]
python3 -m yolozu benchmark \
  --model runs/example/model.pt \
  --onnx-model exports/example.onnx \
  --engine-model exports/example.plan \
  --openvino-model exports/example.xml \
  --data data/coco8.yaml \
  --format torch,onnx,engine,openvino \
  --protocol nms_applied \
  --latency-source auto \
  --output reports/benchmark_report.json
\end{lstlisting}
The OpenVINO runtime and IR remain external to YOLOZU. Missing prerequisites
produce an explicit skipped result.

The primary artifact set is:
\begin{itemize}
  \item \path{reports/benchmark_report.json}
  \item \path{reports/export_settings_<format>.json}
  \item \path{reports/predictions_<format>.json}
  \item \path{reports/eval_<format>.json}
  \item \path{reports/parity_<format>.json}
\end{itemize}

When at least two comparable real results complete successfully for
\cmd{detect}, \cmd{segmentation}, \cmd{keypoints}, \cmd{depth}, or
\cmd{pose6d}, \path{parity_<format>.json} is a real backend-diff artifact. The
chosen reference backend is recorded explicitly (\cmd{auto} prefers
\cmd{torch} when available). Classification and OBB currently write explicit
parity placeholders. Dry-run, skipped, and synthetic-only lanes also keep
parity non-real.

If a detect benchmark should anchor parity on a non-\cmd{torch} backend, set it
explicitly:
\begin{lstlisting}[language=bash]
python3 tools/benchmark_model.py \
  --model runs/example/model.pt \
  --onnx-model exports/example.onnx \
  --data data/coco8.yaml \
  --format torch,onnx \
  --latency-source auto \
  --parity-reference-backend onnx \
  --output reports/benchmark_report.json
\end{lstlisting}
The explicit reference choices are \cmd{torch}, \cmd{onnx}, \cmd{engine},
\cmd{torchscript}, and \cmd{openvino}; OpenVINO selection remains conditional
on a successful comparable result.

\subsection{Benchmark task semantics}
The benchmark surface now records explicit task semantics instead of treating
\cmd{--task} as a loose label. The top-level report and each per-format result
carry the canonical task, the originally requested task, accepted aliases,
metric family, expected metric keys, support level, and whether the task is
part of the mainstream benchmark surface or a YOLOZU-native extension.

The current task matrix is written as task cards instead of a wide table so the
PDF stays readable:
\begin{description}[leftmargin=2.8cm, style=nextline]
  \item[\cmd{detect}]
  Aliases: \cmd{detect}, \cmd{detection}. Metric family: \cmd{bbox_map}.
  Execution support: real for \cmd{torch}, \cmd{onnx}, \cmd{engine}, and
  \cmd{torchscript}, plus conditional \cmd{openvino}. This is the default benchmark path.

  \item[\cmd{segmentation}]
  Aliases: \cmd{segmentation}, \cmd{seg}. Metric family: \cmd{mask_map}.
  Execution support: artifact-backed real eval/parity for \cmd{torch},
  \cmd{onnx}, \cmd{engine}, \cmd{torchscript}, and \cmd{openvino}. Benchmark mode evaluates
  backend mask-prediction artifacts with \path{tools/eval_segmentation.py} and
  compares matched masks directly.

  \item[\cmd{classification}]
  Aliases: \cmd{classification}, \cmd{classify}, \cmd{cls}. Metric family:
  \cmd{topk_accuracy}. Execution support: artifact-backed real eval for
  \cmd{torch}, \cmd{onnx}, \cmd{engine}, \cmd{torchscript}, and \cmd{openvino}. Benchmark mode
  evaluates backend class-score artifacts directly and reports
  \cmd{top1}/\cmd{top5}/\cmd{accuracy} without claiming YOLOZU ran backend
  inference.

  \item[\cmd{obb}]
  Alias: \cmd{obb}. Metric family: \cmd{obb_map}. Execution support:
  artifact-backed real eval for \cmd{torch}, \cmd{onnx}, \cmd{engine}, and
  \cmd{torchscript}, plus \cmd{openvino}. Benchmark mode evaluates backend rotated-box artifacts
  directly and reports OBB metrics without claiming YOLOZU ran backend
  inference.

  \item[\cmd{keypoints}]
  Aliases: \cmd{keypoints}, \cmd{pose}. Metric family: \cmd{oks_map}.
  Execution support: artifact-backed real eval/parity for \cmd{torch},
  \cmd{onnx}, \cmd{engine}, \cmd{torchscript}, and \cmd{openvino}. \cmd{pose} is normalized to
  canonical \cmd{keypoints}; benchmark mode evaluates backend
  \path{predictions.json} artifacts with \path{tools/eval_keypoints.py} and
  compares normalized keypoints directly.

  \item[\cmd{depth}]
  Alias: \cmd{depth}. Metric family: \cmd{depth_error}. Execution support:
  artifact-backed real eval/parity for \cmd{torch}, \cmd{onnx}, \cmd{engine},
  \cmd{torchscript}, and \cmd{openvino}. This is a YOLOZU-native extension that compares backend
  depth artifacts honestly instead of claiming end-to-end benchmark-surface
  parity.

  \item[\cmd{pose6d}]
  Aliases: \cmd{pose6d}, \cmd{6dof}, \cmd{pose_6d}, \cmd{pose-6d}. Metric
  family: \cmd{pose6d_error}. Execution support: artifact-backed real
  eval/parity for \cmd{torch}, \cmd{onnx}, \cmd{engine}, and
  \cmd{torchscript}, plus \cmd{openvino}. This is a YOLOZU-native extension that compares backend
  prediction artifacts honestly instead of claiming end-to-end
  benchmark-surface parity.
\end{description}

For the current implementation, inference-backed real backend execution remains
\cmd{detect}-first. The exceptions are \cmd{classification}, \cmd{obb},
\cmd{segmentation}, \cmd{keypoints}, \cmd{depth}, and \cmd{pose6d}: all may
use \cmd{--latency-source artifact_eval}. For \cmd{classification} and
\cmd{obb}, YOLOZU evaluates backend score or rotated-box artifacts and writes
explicit parity placeholders. For \cmd{segmentation}, YOLOZU evaluates
backend-specific mask-prediction artifacts with \path{tools/eval_segmentation.py}
and then attaches real parity reports over matched sample ids plus per-mask mismatch summaries.
For \cmd{keypoints}, YOLOZU evaluates
backend-specific \path{predictions.json} artifacts with \path{tools/eval_keypoints.py}
and then attaches real parity reports over matched detections plus normalized keypoints.
For \cmd{depth}, YOLOZU evaluates backend-specific depth artifacts (\cmd{.npy}, \cmd{.npz}, or single-channel
image files) against the ground-truth depth artifact and then attaches real
parity reports. For \cmd{pose6d}, YOLOZU evaluates backend-specific
\path{predictions.json} artifacts with \path{tools/eval_pose.py} and then
attaches real parity reports over matched detections plus pose fields such as
rotation, translation, and depth. Formats without shipped benchmark wiring are
reported as unsupported/skipped rather than as synthetic benchmark successes.

\subsection{Backend flag applicability}
Benchmark flags are validated against the task, effective latency source, and
format before output artifacts are written. For \cmd{classification},
\cmd{obb}, \cmd{segmentation}, \cmd{keypoints}, \cmd{depth}, and
\cmd{pose6d}, \cmd{--latency-source auto} resolves to \cmd{artifact_eval} on
real backend formats. Because this lane consumes prepared artifacts rather than
running backend inference, \cmd{--half}, \cmd{--batch} values other than
\cmd{1}, and \cmd{--nms} fail early. The defaults
\cmd{--no-half --batch 1 --no-nms} remain valid.

The same rejection applies when \cmd{artifact_eval} is requested explicitly.
Conversely, \path{dataset_pass_wall_time} is the inference-backed source for
\cmd{detect}. A non-dry-run artifact-backed task forced to that source fails
before writing artifacts and directs the user to \cmd{auto} or
\cmd{artifact_eval}.
With \cmd{--strict}, any requested format that is skipped or fails makes the
command exit with code \cmd{2}.
For non-artifact evaluation, format rules still apply: the current
\cmd{torch} lane can accept these non-default flags, while other current
formats reject them. The complete matrix is generated in
\path{docs/benchmark_support_matrix.md}.

\subsection{Canonical benchmark support matrix}
The source of truth for per-format, per-task artifact status is
\path{docs/benchmark_support_matrix.md}. Use that matrix when deciding whether
a benchmark lane writes real inference artifacts, consumes artifact-backed real
eval/parity inputs, emits dry-run placeholders, or skips because runtime,
artifact, format, or task wiring is unavailable.

The manual intentionally avoids duplicating the full table. When benchmark
semantics change, update the canonical matrix, \path{docs/benchmark_mode.md},
this chapter, \path{tools/manifest.json}, and the packaged manifest copy in the
same change.

\subsection{Runtime / license boundary matrix}
Benchmark support does not imply that a runtime is bundled with YOLOZU. The
repository remains Apache-2.0, but several backends rely on external runtimes
or vendor SDKs with separate terms.

Use these categories instead of reading backend names as license promises:
\begin{description}[leftmargin=3.2cm, style=nextline]
  \item[Real runtime path]
  \cmd{torch}, \cmd{onnx}, \cmd{engine}, and \cmd{torchscript} have real detect
  benchmark paths when the matching local runtime is installed. These runtimes
  are still external to this repository. For \cmd{engine}, verify the Linux,
  NVIDIA GPU, CUDA, TensorRT, and NGC redistribution terms separately.

  \item[Conditional real runtime path]
  \cmd{openvino} has a real detect orchestration path when an external OpenVINO
  runtime and compatible IR artifact are available. Artifact-backed task lanes
  consume supplied files. YOLOZU does not bundle the runtime or model artifact.

  \item[Adapter target only]
  \cmd{executorch} and \cmd{opencv_dnn} are visible adapter targets, but their
  benchmark orchestration is not wired. Benchmark mode reports them as
  unsupported/skipped; standalone exporter utilities may still require
  user-supplied external runtimes. For OpenCV, optional contrib/nonfree modules
  are not bundled.

  \item[Conditional adapter targets]
  \cmd{coreml}, \cmd{ncnn}, \cmd{rknn}, \cmd{tflite}, and
  \cmd{paddle} are not bundled runtimes. Treat them as conditional
  adapter targets unless the support matrix explicitly says a real lane exists
  for the selected task and format.
\end{description}

\subsection{Gap against the benchmark/export surface}
Relative to the broader benchmark/export surface users now expect, YOLOZU has
already matched the core benchmark entrypoint shape, but it still trails in
surface breadth.

The most important remaining gaps are:
\begin{itemize}
  \item broader format coverage beyond conditional \cmd{openvino}, such as
  \cmd{coreml}, \cmd{saved_model}, \cmd{tflite}, \cmd{ncnn}, \cmd{rknn}, and
  \cmd{paddle}
  \item broader parity attachment for artifact-backed \cmd{classification} and
  \cmd{obb} lanes
  \item additional task/source/format validation as new backend-specific knobs
  and execution paths are added
\end{itemize}

\subsection{Highest-leverage parity maintenance and remaining work}
If the goal is to close the practical gap against the broader benchmark/export
surface, preserve the shipped boundaries and implement the remaining parity
attachment in this order:
\begin{enumerate}
  \item keep conditional \cmd{openvino} honest on the same canonical CLI surface as the other real backend lanes
  \item keep \path{docs/benchmark_support_matrix.md} as the single support matrix that distinguishes real inference/eval/parity
  from dry-run placeholders and unsupported/skipped paths
  \item add real parity to the artifact-backed \cmd{classification} and
  \cmd{obb} lanes after their validation and metric semantics are
  evidence-backed
  \item keep format-specific flag validation strict so inert combinations fail
  early rather than appearing supported
\end{enumerate}

This order keeps the interface contract stable, improves user-visible parity
quickly, and preserves YOLOZU's Apache-2.0 repository operations policy.

This comparison is intentionally about interface behavior and user-facing
surface only. YOLOZU keeps its Apache-2.0-only repository operations policy and
must not pull GPL-licensed implementation code into the repository while
closing these gaps.

The same boundary logic applies to training-side integrations: prefer the
Apache-2.0-friendly YOLOX external lane first, and keep optional Ultralytics
bridges explicitly separated rather than treating them as equivalent defaults.

For repository-side orchestration, the equivalent wrapper is
\path{tools/benchmark_model.py}.

The benchmark harness, located at \path{tools/benchmark_latency.py}, generates:
\begin{itemize}
  \item A stable JSON report (detailing a single run).
  \item A JSONL history file (facilitating append-only trend tracking).
\end{itemize}

This harness supports both synthetic timing evaluations and configuration-driven, per-bucket executions. In the latter mode, each bucket can ingest externally measured metrics via JSON (for instance, data generated by TensorRT latency measurement scripts).

Typically tracked metrics include FPS and latency quantiles (mean, p50, p90, p95, and p99).

\section{Sweeps}
A sweep harness is indispensable for systematically comparing numerous runs or configurations.

The sweep runner, \path{tools/hpo_sweep.py}, is entirely framework-agnostic and operates by executing templated commands. The core configuration model comprises:
\begin{itemize}
  \item \texttt{base\_cmd}: The command template containing \texttt{\{param\}} placeholders.
  \item \texttt{param\_grid} or \texttt{param\_list}: The defined hyperparameter search space.
  \item Optional keys for metrics extraction and designated output destinations.
\end{itemize}

The default artifacts are designed for effortless diffing and publication:
\path{reports/hpo_sweep.jsonl}, \path{reports/hpo_sweep.csv}, and \path{reports/hpo_sweep.md}.
Utilize the \cmd{--resume} flag to intelligently bypass previously completed parameter combinations.
