\section{Design Philosophy}
The CLI surface now has one supported top-level entrypoint plus a compatibility shim:
\begin{itemize}
  \item \cmd{yolozu} / \cmd{python3 -m yolozu}: the supported top-level CLI.
  \item \cmd{python3 tools/yolozu.py}: a legacy compatibility wrapper for older repo-local scripts.
\end{itemize}

This chapter documents the \textit{high-traffic commands} on the supported surface and points directly to repo-only helper scripts when a workflow does not belong on the top-level CLI.

\paragraph{Stable parent entrypoints do not promote opt-in lanes.}
The \texttt{stable} manifest label on \cmd{yolozu} describes the parent
entrypoint and its core validation/evaluation lane. Benchmark and training
sub-lanes retain their separately declared capability or backend maturity, and
research adaptation flags remain Research.
Likewise, \path{tools/export_predictions.py} has a Stable baseline export path,
while optional acceleration flags require backend/device qualification,
opt-in TTA is Experimental, and opt-in TTT is Research. The default TTA mode
transforms exported predictions; \texttt{rtdetr\_pose} model mode reruns one
augmented inference branch and merges it without updating model parameters. Use
\path{docs/production_readiness.md} for the capability-level source of truth.

\section{Discoverability}
As a best practice, always initiate discovery with:\\
\cmd{yolozu --help} and \cmd{yolozu <command> --help}.\\
In a source checkout, \cmd{python3 -m yolozu --help} is equivalent. The legacy \cmd{python3 tools/yolozu.py --help} wrapper is compatibility-only.

Manual drift is guarded by \cmd{python3 tools/audit_manual_cli_drift.py}.
When the top-level CLI changes, update this chapter and only extend
\path{docs/manual_cli_drift_allowlist.json} for intentional prose placeholders
or repo-only helpers, not for real \cmd{yolozu} commands.

\paragraph{Where did the long command descriptions go?}
This table is intentionally an entrypoint map, not the full CLI reference. Use
\path{docs/generated/cli_reference.md} for the generated command and manifest
surface.
For complete option lists, use \cmd{--help}. For repository helper metadata,
use \path{tools/manifest.json}. When this chapter changes, run
\cmd{python3 tools/audit_manual_cli_drift.py} so the manual stays aligned with
the implemented CLI surface.

\paragraph{Shortest strict evaluation.}
\cmd{yolozu eval-coco} performs strict predictions validation before
conversion or scoring, so a separate validation command is optional. Use
\cmd{--dry-run} when COCO metrics are not required. Legacy coercion is available
only through explicit \cmd{--repair}; each repair is recorded in report
\path{warnings}. A failed run writes \path{status=failed} at the requested
output path instead of leaving stale success evidence.

\subsection{Long-tail recipe plugin options (PyTorch)}
\cmd{yolozu long-tail-recipe} supports explicit plugin choices for loss, validation metric, and learning-rate scheduler.

\begin{lstlisting}[language=bash]
yolozu long-tail-recipe \
  --dataset data/smoke --split val \
  --loss-plugin torch_cross_entropy \
  --metric-plugin torch_top1_accuracy \
  --lr-scheduler torch_step_lr \
  --output reports/long_tail_recipe_torch.json --force
\end{lstlisting}

Primary plugin flags:
\begin{itemize}
  \item \cmd{--loss-plugin}: \path{none}, \path{focal}, \path{ldam},\\
  \path{torch_cross_entropy}, \path{torch_nll_loss}, \path{torch_bce_with_logits}
  \item \cmd{--metric-plugin}: \path{none}, \path{torch_top1_accuracy},\\
  \path{torch_top5_accuracy}, \path{torch_cross_entropy}
  \item \cmd{--lr-scheduler}: \path{none}, \path{torch_step_lr},\\
  \path{torch_cosine_annealing_lr}, \path{torch_reduce_on_plateau},\\
  \path{torch_one_cycle_lr}
\end{itemize}

\end{lstlisting}

For comprehensive details regarding the backbone interface contract and supported architectures, refer to \path{docs/backbones.md}.

\subsection{Test YAML and the Override Rule}
The default test YAML configuration is intentionally minimalist (typically specifying only the adapter, dataset, split, and max\_images). Runtime-specific parameters are conventionally supplied as CLI overrides:
\begin{lstlisting}[language=bash]
yolozu test configs/examples/test_setting.yaml \
  --adapter rtdetr_pose \
  --config rtdetr_pose/configs/base.json \
  --checkpoint /path/to/checkpoint.pt \
  --dataset data/smoke \
  --max-images 50
\end{lstlisting}

\noindent This paradigm directly mirrors the documented real-model workflow detailed in \path{docs/real_model_interface.md}.
