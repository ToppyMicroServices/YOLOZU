\section{What YOLOZU means by ``continual''}
Continual learning (CL) here means fine-tuning across a sequence of tasks/domains while mitigating catastrophic forgetting.
In this repository, the reference implementation targets the in-repo \path{rtdetr_pose} training stack.

\section{Core approach (baseline)}
The default strategy combines:
\begin{itemize}
  \item \textbf{Memoryless self-distillation}: keep the new model close to the previous checkpoint while learning the new task.
  \item \textbf{Optional replay buffer}: add a small buffer of past samples (e.g., reservoir sampling) and train on \emph{(current task + replay)}.
  \item \textbf{Optional parameter-efficiency}: restrict trainable parameters (e.g., LoRA) to reduce forgetting pressure.
\end{itemize}

\section{Online learning, continual learning, and TTT are not the same thing}

These three ideas are often grouped together because all of them react to distribution shift.
Operationally, however, they solve different problems and carry different risk.

\begin{center}
\begin{tabular}{p{0.20\linewidth}p{0.23\linewidth}p{0.23\linewidth}p{0.24\linewidth}}
\toprule
Approach & What changes & Main goal & Main operational risk \\
\midrule
Online learning & model weights are updated close to inference time & adapt immediately to fresh data & bad labels or drift can corrupt production behavior quickly \\
Continual learning & model weights are updated in staged retraining runs & learn new tasks/domains while limiting forgetting & forgetting old behavior or promoting a weak checkpoint \\
TTT (test-time training / adaptation) & temporary inference-time adaptation or state adjustment & stabilize predictions on the current batch / scene & mixing short-lived adaptation with long-lived training decisions \\
\bottomrule
\end{tabular}
\end{center}

The short version is:
\begin{itemize}
  \item \textbf{online learning} is the fastest to react, but also the easiest to destabilize,
  \item \textbf{continual learning} is slower, but much easier to audit and govern,
  \item \textbf{TTT} is best thought of as \emph{inference-time correction}, not as the main mechanism for long-term knowledge accumulation.
\end{itemize}

\section{Safe design pattern in \yolozu{}}

For this repository, the safest default is \textbf{not} ``train the production model while it is serving''.
Instead, use \yolozu{} as a governed loop with explicit boundaries:
\begin{enumerate}
  \item keep production inference separate from retraining,
  \item collect inputs, predictions, and review signals as artifacts,
  \item select candidate retraining data from those artifacts,
  \item run continual-learning jobs off the serving path,
  \item evaluate old-task retention and new-task adaptation before promotion.
\end{enumerate}

This is where the repository fits naturally:
\begin{itemize}
  \item \textbf{prediction capture}: keep outputs and settings under a predictions interface contract,
  \item \textbf{candidate selection}: choose low-confidence, failed, or newly labeled examples for retraining,
  \item \textbf{continual training}: use replay and/or self-distillation to reduce catastrophic forgetting,
  \item \textbf{evaluation}: compare old tasks and new tasks before a checkpoint is promoted.
\end{itemize}

\subsection{Recommended control-plane split}

The practical split is:
\begin{itemize}
  \item \textbf{serving plane}: inference only,
  \item \textbf{data plane}: collect predictions, labels, and failure cases,
  \item \textbf{training plane}: run continual-learning jobs,
  \item \textbf{promotion plane}: gate model release on retention + adaptation metrics.
\end{itemize}

This separation matters because it prevents a weak pseudo-labeling step or a bad domain shift from mutating the live model immediately.

\subsection{What to do with TTT}

TTT is still useful in \yolozu{}, but for a different reason:
\begin{itemize}
  \item use it to stabilize predictions under a temporary shift,
  \item log what happened,
  \item do \emph{not} automatically treat that short-lived adaptation as an approved training update.
\end{itemize}

In other words:
\begin{quote}
TTT can help the current prediction, but continual learning should decide the next checkpoint.
\end{quote}

\subsection{A safe operator checklist}

If you want to introduce adaptation without destabilizing production, the safest order is:
\begin{enumerate}
  \item start by logging predictions and failures,
  \item build a reviewed retraining set or a tightly filtered pseudo-label set,
  \item run a separate continual-learning job,
  \item compare retention on older tasks and adaptation on the new task,
  \item promote only if the checkpoint passes the gate,
  \item keep TTT separate from automatic checkpoint promotion.
\end{enumerate}

For most teams, this means:
\begin{quote}
prefer continual learning as the default production-update loop, and use online learning or TTT only where the risk is well understood and explicitly bounded.
\end{quote}

\subsection{Automating the promotion decision in \yolozu{}}

The repository can automate the \emph{decision layer} even when the data curation and retraining steps remain separate.
The intended pattern is:
\begin{enumerate}
  \item run continual training,
  \item run \cmd{eval\_continual.py},
  \item feed the resulting eval report into \cmd{continual\_decide.py},
  \item promote only if the decision report says \cmd{promote}.
\end{enumerate}

Example:
\begin{lstlisting}[language=bash]
python3 tools/continual_decide.py \
  --eval-json runs/continual/<run>/continual_eval.json \
  --run-json runs/continual/<run>/continual_run.json \
  --max-forgetting 0.05 \
  --min-new-task-score 0.40 \
  --min-old-task-final 0.40 \
  --min-reviewed-labels 20 \
  --min-highconf-pseudo-labels 50 \
  --min-total-curated-examples 60
\end{lstlisting}

For CI or batch ops, the same pattern is:
\begin{lstlisting}[language=bash]
python3 tools/eval_continual.py \
  --run-json runs/continual/<run>/continual_run.json \
  --device cpu \
  --max-images 50

python3 tools/continual_decide.py \
  --eval-json runs/continual/<run>/continual_eval.json \
  --run-json runs/continual/<run>/continual_run.json \
  --curation-json reports/continual_curation.json \
  --max-forgetting 0.05 \
  --min-new-task-score 0.40 \
  --min-old-task-final 0.40 \
  --min-reviewed-labels 20 \
  --min-highconf-pseudo-labels 50 \
  --min-total-curated-examples 60
\end{lstlisting}

This writes a decision report (by default \path{runs/continual/<run>/continual\_promotion\_decision.json}) with one of three outcomes:
\begin{itemize}
  \item \cmd{hold}: hard gate failed,
  \item \cmd{review}: hard gates passed, but a soft review gate still requires operator confirmation,
  \item \cmd{promote}: the checkpoint is eligible for promotion under the configured policy.
\end{itemize}

The soft-gate idea is deliberate.
For example, reviewed labels and trusted pseudo-label counts can support a promotion decision, but they should not replace actual old-task/new-task evaluation.

Minimal curation summary:
\begin{lstlisting}[language=json]
{
  "counts": {
    "samples_total": 1200,
    "candidate_images": 90,
    "reviewed_labels": 48,
    "pseudo_labels_high_confidence": 120
  }
}
\end{lstlisting}

Recommended batch/CI curation summary:
\begin{lstlisting}[language=json]
{
  "counts": {
    "samples_total": 1200,
    "candidate_images": 90,
    "reviewed_labels": 48,
    "pseudo_labels_high_confidence": 120
  },
  "sources": {
    "review_queue": "reports/review_queue.json",
    "pseudo_label_run": "reports/pseudo_labels.json"
  },
  "serving": {
    "ttt_active": false
  }
}
\end{lstlisting}

If TTT was active on the serving path, the safe default is still to require review:
\begin{quote}
use TTT to help the current prediction, but let continual-learning evaluation decide the next checkpoint.
\end{quote}

\section{LoRA / QLoRA in plain language}
LoRA and QLoRA are not separate continual-learning algorithms.
They are \textbf{ways to make the parameter updates smaller and cheaper}.

\subsection{LoRA}
The easiest mental model is:
\begin{quote}
freeze most of the big model, then train a much smaller correction on top.
\end{quote}

That is why LoRA is attractive in continual learning:
\begin{itemize}
  \item a smaller trainable surface can reduce forgetting pressure,
  \item it is often easier to fit within a limited GPU budget,
  \item it gives a more controlled ablation than full-model fine-tuning.
\end{itemize}

\textbf{What actually gets updated.}
This is the part that is easiest to miss if you only hear the slogan.
LoRA usually keeps the original pretrained weight $W$ frozen and learns a small low-rank correction:
\[
W' = W + \Delta W, \qquad \Delta W = BA.
\]
Here, $A$ and $B$ are the trainable adapter matrices.
Operationally, that means:
\begin{itemize}
  \item the backbone knowledge remains mostly anchored in the frozen weight,
  \item the new task/domain signal is expressed through a smaller correction,
  \item replay and self-distillation still do the anti-forgetting work; LoRA only narrows the update surface.
\end{itemize}

\subsection{QLoRA}
QLoRA keeps the same adapter idea, but stores the frozen base model in a more memory-efficient quantized form.

In plain language:
\begin{itemize}
  \item \textbf{LoRA}: freeze the large model, train small adapters.
  \item \textbf{QLoRA}: do the same thing, but keep the frozen base cheaper to hold in memory.
\end{itemize}

So the update logic is still LoRA-style:
\begin{itemize}
  \item the adapters move,
  \item the frozen base remains the reference,
  \item quantization changes storage/runtime cost, not the continual-learning objective.
\end{itemize}

\subsection{Pros and Cons}
\textbf{LoRA}
\begin{itemize}
  \item Pros: simpler mental model than QLoRA; often cheaper than full fine-tuning; integrates naturally with replay and self-distillation.
  \item Cons: still introduces extra knobs; can underfit if the adapter is too small; may hide the fact that the base model is the real bottleneck.
\end{itemize}

\textbf{QLoRA}
\begin{itemize}
  \item Pros: lowers memory pressure further; keeps the adapter-style workflow; attractive when the frozen base dominates footprint.
  \item Cons: adds quantization complexity; depends on backend support; is more experimental in this repository than plain LoRA.
\end{itemize}

\subsection{A practical choice example}
Imagine a domain-incremental warehouse-camera project:
\begin{itemize}
  \item the previous checkpoint is already usable,
  \item the main concern is forgetting older camera views,
  \item GPU memory is limited, but not critically constrained.
\end{itemize}

In that situation, \textbf{LoRA is usually the better first experiment}.
It keeps the story simpler: replay + self-distillation still do the anti-forgetting work, while the adapter merely reduces how much of the model moves.

Now change one assumption:
\begin{itemize}
  \item the frozen base is the real memory bottleneck,
  \item batch size collapses unless the base becomes cheaper to hold.
\end{itemize}

That is when \textbf{QLoRA becomes the practical option}.
You keep the same adapter-style update logic, but trade some simplicity for a smaller memory footprint.

So the operational rule is:
\begin{itemize}
  \item \textbf{LoRA first when clarity and debugging speed matter},
  \item \textbf{QLoRA when memory is the real blocker}.
\end{itemize}

python3 rtdetr_pose/tools/train_continual.py \

To run \textbf{memoryless} (no replay), set replay size to 0 in the config.

\paragraph{Note on "distillation" terminology}
This chapter's \emph{distillation} refers to \textbf{checkpoint-based self-distillation during training} (e.g., \cmd{--self-distill-from}) as an anti-forgetting mechanism.
The separate tool \path{tools/distill_predictions.py} performs \textbf{offline prediction blending} (rewriting a predictions JSON) and does not by itself mitigate catastrophic forgetting.

\section{How to add SDFT to an RT-DETR / YOLO-style image model}

For detector-style image models, SDFT does \textbf{not} mean inventing a new architecture.
It means adding two pieces to an existing training loop:
\begin{itemize}
  \item a \textbf{frozen teacher checkpoint} from the previous stage,
  \item a \textbf{distillation loss} that keeps the current student close to that teacher while learning the new task.
\end{itemize}

\subsection{The roles of student and teacher}

The simplest mental model is:
\begin{itemize}
  \item \textbf{student}: the model we are updating on the new task/domain,
  \item \textbf{teacher}: the previous checkpoint, loaded once and kept frozen.
\end{itemize}

So one training step becomes:
\begin{enumerate}
  \item run the current image batch through the student,
  \item run the same batch through the frozen teacher,
  \item compute the usual task loss against labels,
  \item compute a distillation loss between student outputs and teacher outputs,
  \item add them together and update the student only.
\end{enumerate}

In compact form:
\[
\mathcal{L}_{total} = \mathcal{L}_{task} + \lambda \mathcal{L}_{distill}.
\]

Here, $\lambda$ controls how strongly the new run is pulled toward the previous checkpoint.

\subsection{What to distill in detector-style models}

For RT-DETR / YOLO-like models, the most practical distillation targets are:
\begin{itemize}
  \item \textbf{classification logits}: keep class confidence behavior close to the previous checkpoint,
  \item \textbf{bounding boxes}: keep localization from drifting too far,
  \item optional task heads such as \textbf{segmentation}, \textbf{depth}, \textbf{keypoints}, or \textbf{pose}, when those outputs exist in both teacher and student.
\end{itemize}

The repository's default continual path describes the common baseline as:
\begin{quote}
logits + bbox distillation, with reverse-KL on logits by default.
\end{quote}

That is a good first configuration because it directly targets the two outputs most likely to regress during detector fine-tuning: classification behavior and localization behavior.

\subsection{What changes in the training loop}

Conceptually, the existing training loop stays the same.
The only difference is that the batch now has two forward passes:

\begin{lstlisting}[language=Python]
student_outputs = student(images)

with torch.no_grad():
    teacher_outputs = teacher(images)

task_loss = compute_task_loss(student_outputs, targets)
distill_loss = compute_distill_loss(student_outputs, teacher_outputs)
total_loss = task_loss + lambda_distill * distill_loss

optimizer.zero_grad()
total_loss.backward()
optimizer.step()
\end{lstlisting}

Three practical rules matter:
\begin{itemize}
  \item the teacher checkpoint is loaded once and kept in \cmd{eval()} mode,
  \item the teacher is never optimized,
  \item teacher and student must expose compatible output keys for the chosen distillation targets.
\end{itemize}

\subsection{How this maps to YOLOZU}

In this repository, the operator-facing hook is the frozen-teacher flag:
\begin{lstlisting}[language=bash]
--self-distill-from /path/to/previous_stage.ckpt
\end{lstlisting}

That means the practical recipe is:
\begin{enumerate}
  \item train Task A or Domain A normally and save a checkpoint,
  \item start Task B / Domain B fine-tuning from the current initialization,
  \item also pass the previous checkpoint as the frozen teacher,
  \item keep the usual detection loss, and add distillation on logits / bbox (plus optional extra heads).
\end{enumerate}

At the CLI level, the continual runner does this through the sequential training path:
\begin{lstlisting}[language=bash]
python3 rtdetr_pose/tools/train_continual.py \
  --config configs/continual/rtdetr_pose_domain_inc_example.yaml
\end{lstlisting}

And the manual low-level mental model is:
\begin{itemize}
  \item \cmd{train\_minimal.py}: the per-stage trainer,
  \item \cmd{--self-distill-from}: the frozen teacher checkpoint input,
  \item continual config: controls replay, distillation keys, and distillation weight.
\end{itemize}

\subsection{Why this helps}

Without SDFT, fine-tuning on the new task can move detector outputs too aggressively toward the new data distribution.
In practice, that often shows up as:
\begin{itemize}
  \item older classes becoming miscalibrated,
  \item box quality drifting on previous domains,
  \item task-specific heads regressing even when the backbone still looks reasonable.
\end{itemize}

SDFT does not stop the model from learning the new task.
Instead, it adds a second pressure:
\begin{quote}
learn the new data, but do not move so far that the previous detector behavior collapses.
\end{quote}

\subsection{A minimal operator recipe}

If you already have an existing RT-DETR / YOLO-style checkpoint, the operational sequence is:
\begin{enumerate}
  \item keep the previous checkpoint,
  \item fine-tune on the new dataset/domain,
  \item pass the previous checkpoint as \cmd{--self-distill-from},
  \item start with logits + bbox distillation,
  \item only later add replay, LoRA, or extra task-head distillation if needed.
\end{enumerate}

This is usually the cleanest first experiment because it answers the central question quickly:
\begin{quote}
Can the model adapt to the new data without forgetting too much of the previous detector behavior?
\end{quote}

\subsection{Measured smoke run: naive sequential fine-tune vs memoryless SDFT}

To make the workflow concrete, we ran a tiny two-task continual-learning smoke experiment in this repository.
This was not intended as a benchmark.
Its purpose was to verify that the SDFT path really executes, records the teacher checkpoint, and emits the expected continual-learning artifacts.

\paragraph{Setup.}
We created two tiny task roots from \path{data/coco128}:
\begin{itemize}
  \item Task A: 8 train images + 4 val images,
  \item Task B: 8 train images + 4 val images.
\end{itemize}

Both runs used the same detector config and the same tiny budget:
\begin{itemize}
  \item device: CPU,
  \item image size: $160$,
  \item batch size: $1$,
  \item max steps per task: $2$,
  \item replay: disabled (\cmd{replay\_size: 0}).
\end{itemize}

We then executed two runs:
\begin{itemize}
  \item \textbf{naive sequential fine-tune}: Task B resumes from Task A, but uses no teacher checkpoint,
  \item \textbf{memoryless SDFT}: Task B resumes from Task A and also receives \cmd{--self-distill-from} pointing to the Task A checkpoint.
\end{itemize}

\paragraph{Commands.}
The measured runs were produced with:
\begin{lstlisting}[language=bash]
python3 rtdetr_pose/tools/train_continual.py \
  --config /tmp/yolozu_sdft_manual_naive.yaml \
  --run-dir runs/continual/manual_sdft_smoke_naive

python3 rtdetr_pose/tools/train_continual.py \
  --config /tmp/yolozu_sdft_manual_sdft.yaml \
  --run-dir runs/continual/manual_sdft_smoke_sdft
\end{lstlisting}

And evaluated with:
\begin{lstlisting}[language=bash]
python3 tools/eval_continual.py \
  --run-json runs/continual/manual_sdft_smoke_naive/continual_run.json \
  --device cpu \
  --image-size 160 \
  --max-images 4 \
  --metric simple_map \
  --force

python3 tools/eval_continual.py \
  --run-json runs/continual/manual_sdft_smoke_sdft/continual_run.json \
  --device cpu \
  --image-size 160 \
  --max-images 4 \
  --metric simple_map \
  --force
\end{lstlisting}

\paragraph{Observed results.}
The important thing to notice is not a claimed accuracy gain, but that the SDFT path became visible in the recorded outputs:
\begin{center}
\begin{tabular}{@{}p{1.6cm}p{2.8cm}p{2.5cm}p{6.4cm}@{}}
\toprule
Run & Task B teacher & Task B final loss & Extra recorded loss terms \\
\midrule
Naive & none & 2.673 & none \\
SDFT & Task A checkpoint & 1.975 & \cmd{loss\_sdft}=0.187,\ \cmd{loss\_sdft\_bbox}=0.057,\ \cmd{loss\_sdft\_logits}=0.130 \\
\bottomrule
\end{tabular}
\end{center}

More specifically:
\begin{itemize}
  \item \path{runs/continual/manual\_sdft\_smoke\_sdft/task01\_task\_b/run\_record.json} recorded \cmd{self\_distill\_from} pointing to the Task A checkpoint.
  \item \path{runs/continual/manual\_sdft\_smoke\_sdft/task01\_task\_b/metrics.json} contained \cmd{loss\_sdft}, \cmd{loss\_sdft\_bbox}, and \cmd{loss\_sdft\_logits}, which do not appear in the naive run.
  \item Both runs wrote the expected continual-learning outputs: \path{continual\_run.json}, per-task checkpoints, per-task metrics, and \path{continual\_eval.json}.
\end{itemize}

\paragraph{What this smoke run does \emph{not} prove.}
Because this validation run used only two optimization steps per task and only four validation images per task, the proxy mAP matrix stayed at zero for both runs.
That means this example should be read as a \emph{wiring and artifact validation}, not as evidence that SDFT improved accuracy in this tiny setting.

The right interpretation is:
\begin{quote}
the teacher path executed correctly, the distillation loss was active on Task B, and the continual-learning artifacts were emitted in a form that can be inspected and compared.
\end{quote}

\begin{lstlisting}[language=bash]
python3 tools/eval_continual.py \
  --run-json runs/continual/<run>/continual_run.json \
  --device cpu \
  --max-images 50 \
  --metric pose \
  --metric-key pose_success
\end{lstlisting}

Available \cmd{--metric-key} values in pose mode:
\begin{itemize}
  \item \cmd{pose_success}, \cmd{rot_success}, \cmd{trans_success}, \cmd{match_rate}, \cmd{iou_mean}
  \item \cmd{depth_abs_mean}, \cmd{depth_abs_median}
  \item \cmd{add_mean}, \cmd{add_median}, \cmd{adds_mean}, \cmd{adds_median}
\end{itemize}

Notes:
\begin{itemize}
  \item Depth metrics require GT depth/translation and predicted depth/translation fields.
  \item ADD/ADDS metrics require CAD points in sidecar metadata (\cmd{cad_points} / \cmd{cad_path} / \cmd{cad_points_path}) and valid GT+pred pose.
\end{itemize}

Examples for metric-key switching:
\begin{lstlisting}[language=bash]
# depth error summary
python3 tools/eval_continual.py \
  --run-json runs/continual/<run>/continual_run.json \
  --metric pose \
  --metric-key depth_abs_mean

# ADD / ADDS (requires CAD points)
python3 tools/eval_continual.py \
  --run-json runs/continual/<run>/continual_run.json \
  --metric pose \
  --metric-key add_mean

python3 tools/eval_continual.py \
  --run-json runs/continual/<run>/continual_run.json \
  --metric pose \
  --metric-key adds_mean
\end{lstlisting}

\section{Run artifacts (what to version / what to compare)}
\cmd{train_continual.py} writes a run folder under \path{runs/continual/}.
Key outputs:
\begin{itemize}
  \item \path{continual_run.json}: task list, checkpoints, config hash, and run record.
  \item \path{replay_buffer.json}: buffer summary (when replay is enabled).
  \item Per-task subfolders, typically including:\\
    \path{checkpoint.pt}, \path{metrics.jsonl}, \path{metrics.csv}, \path{run_record.json}.
\end{itemize}

For reporting and plots, treat \path{continual_run.json} as the single source of truth.

\section{Selected config knobs (high leverage)}
Commonly tuned items include:
\begin{itemize}
  \item Replay: \cmd{replay_size}, \cmd{replay_fraction}, \cmd{replay_per_task_cap}.
  \item Distillation: \cmd{distill.enabled}, \cmd{distill.keys}, \cmd{distill.weight}, \cmd{distill.temperature}.
  \item Replay distillation (DER++-style): \cmd{derpp.enabled} and related keys (requires teacher outputs stored in records).
  \item Regularizers across tasks (optional): EWC (\cmd{ewc.*}) and SI (\cmd{si.*}).
\end{itemize}

\section{Research workflow guidance}
\begin{itemize}
  \item \textbf{Pin the evaluation subset}: use a deterministic subset (same images each run) before comparing CL runs.
  \item \textbf{Log runtime cost}: replay and distillation change throughput; report accuracy vs cost.
  \item \textbf{Keep baselines simple}: compare (A) naive fine-tune, (B) memoryless self-distill, (C) replay+distill.
\end{itemize}

\section{Notes}
\begin{itemize}
  \item Some continual comparisons use a CPU-friendly proxy metric (e.g., a lightweight mAP-style summary) on a pinned subset to keep iteration fast.
  \item For ``real'' mAP, switch your evaluation workflow to a full COCO evaluator when appropriate.
\end{itemize}
